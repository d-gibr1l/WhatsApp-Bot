### Observation 1.2: Fallback to Global Session-Wide Rate Limiting
In `src/auth/badMacInterceptor.js`, `handleInterceptedLog` constructs `rateLimitKey` as follows (lines 253–254, 273–274):

And in `_unhandledHandler` (lines 299–301):
```javascript

301:       const macKey = keyInfo ? `unhandled:mac:${sessionId}:${keyInfo.id}` : `unhandled:mac:${sessionId}`;
```

When `extractKeyId()` returns `null` (because the error object or string format lacks a standard JID or Signal address pattern), `rateLimitKey` evaluates to `console:mac:${sessionId}` or `unhandled:mac:${sessionId}`. `isRateLimited()` flags this key as logged for 10 seconds (`RATE_LIMIT_MS = 10_000`). Consequently, a single error with an unextractable key suppresses Bad MAC log warnings globally across all chats for the next 10 seconds.

### Observation 1.6: Duplicate and Lossy `unhandledRejection` Handlers
In `index.js` (lines 138–148):

Both `index.js` and `badMacInterceptor.js` register `unhandledRejection` listeners on `process`. `index.js` unconditionally drops any rejection matching `'Bad MAC'`. ## 2. Logic Chain

### 2.1 How Bad MAC decryption errors are currently caught, handled, or suppressed
1. **Console Shimming (Layer 1):** Baileys logs Signal decryption errors to `console.error` and `console.log`. `badMacInterceptor.js` patches `console.error` and `console.log`. It checks `isSuppressible(...args)`. If suppressible, `handleInterceptedLog` extracts `keyInfo` via `extractKeyId()`, checks rate limiting (`isRateLimited()`), outputs a single formatted log line if not rate limited, and calls `purgeForBadMac(keyInfo)`.
2. **Unhandled Rejection Listener (Layer 2):** Uncaught decryption promises trigger `process.on('unhandledRejection')`. `badMacInterceptor.js` checks if the error message includes `'Bad MAC'` or `'MessageCounterError'`. If matched, it rate-limits the error log and calls `purgeForBadMac(keyInfo)`.
3. **Flaw:** If a suppressible log matches patterns like `'Session error:'` or `'Failed to decrypt message'`, `handleInterceptedLog` lacks a matching `if` clause, resulting in **complete silent log suppression**.

### 2.2 Is rate-limiting of Bad MAC errors currently global or per-chat (per-chat JID)?
1. Rate limiting is **partially per-chat** when `extractKeyId()` succeeds in finding a valid JID or Signal address (e.g. `console:mac:${sessionId}:123456789.0`).
2. However, rate limiting **collapses to GLOBAL per session** (`console:mac:${sessionId}` or `unhandled:mac:${sessionId}`) whenever `extractKeyId()` fails to parse a key ID (returning `null`).
3. When global fallback occurs, a single un-extractable error silences error warnings for **ALL CHATS** across the entire bot for 10 seconds. Furthermore, key purging is skipped when `keyInfo` is `null`.

### 2.3 Does error handling globally suppress vital log messages or hide critical disconnect reasons?
1. **Yes, log messages are globally suppressed:**
   - `handleInterceptedLog` drops 5 out of 7 `SUPPRESS_PATTERNS` silently without printing any log output.
   - `pino({ level: "silent" })` in `index.js` silences all internal Baileys warnings, stream errors, and handshake failure diagnostics.
2. **Yes, critical disconnect reasons are hidden:**
   - In `index.js` (`connection === "close"`), `lastDisconnect.error.message`, stack trace, and root cause are completely omitted. Operators only see generic strings like `Disconnected: Unknown (undefined)` or `Disconnected: connectionClosed (428)`.

### 2.4 How Bad MAC error handling should be refactored
1. **Safely Scope Rate-Limiting Per-Chat JID:**
   - Refactor `extractKeyId()` to extract JIDs from all Baileys error types and stack traces.
   - If key extraction fails, fallback to a distinct non-colliding fallback key (`console:mac:${sessionId}:unknown_jid`) so per-chat rate limits for known JIDs remain unaffected.
2. **Eliminate Silent Log Drops:**
   - Add a fallback handler in `handleInterceptedLog()` for all suppressible patterns to print rate-limited structured log messages.
3. **Fix Circuit Breaker Empty JID Guard:**
   - In `badMacInterceptor.js`, return early if `!baseJid` to avoid tracking bad MAC counts for empty strings.
   - In `redisSession.js`, abort `purgeAllKeysForJid(jid)` if `!jid` or `!base` to prevent generating the glob pattern `${sessionId}:session-.*` that wipes all sessions.
4. **Restore Diagnostic Logging Visibility:**
   - Configure Pino log level via environment variable (e.g. `process.env.LOG_LEVEL || "warn"`).
   - In `index.js` connection close handler, log `lastDisconnect.error.message` and stack trace.

## 4. Caveats

- **Network-level decryption failures:** Physical network packet loss or corrupted WebSocket frames below Baileys cannot be fixed at the application layer; the interceptor relies on Baileys signaling these errors to console/rejections.
- **External dependencies:** `@whiskeysockets/baileys` and `libsignal` error format changes across versions could affect regex pattern matching in `extractKeyId()`.

---

## 5. Conclusion

The Bad MAC interceptor and error handling logic contain critical vulnerabilities—most notably a catastrophic bug where empty JIDs trigger a global session wipe (`${sessionId}:session-.*`) in Redis, and high-severity log suppression where non-BadMAC decryption errors are silently erased from console output. Implementing the recommended per-chat JID rate limiting, empty JID guards, and logging visibility fixes will eliminate session loss risks while providing clear operational visibility.
